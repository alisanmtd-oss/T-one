# Shopee continuous training loop

Run only incremental Shopee learning; never open the 14GB raw session.

## Knowledge-package-first search order

Before public-policy browsing, inventory the unique Shopee Skill/rules/course/templates/checklists/evaluations/failures/connectors and `config/github_capability_registry.json`, then choose the exact missing capability. Spend at least 50% of the round on English candidate discovery, source audit, reuse and deduplication; generic official home/About/navigation pages stay below 10%. Use targeted official deep pages only to verify sampled current rules, permissions, API fields/errors, sites and store modes.

Start with `Shopee seller agent skills`, `Shopee operations playbook`, `Shopee ads automation`, `Shopee Open Platform SDK`, and `Shopee marketplace ERP integration`. Cross them with `repo/topic/awesome/skill/playbook/SOP/checklist/template/evaluation/SDK/MCP/ERP/OMS/PIM/WMS`. Extend only when relevant with `ecommerce agent skills`, `marketplace seller agent`, `commerce MCP`, `multichannel ecommerce ERP`, `commerce operations playbook`, `seller SOP`, `retail analytics agent`, `order inventory fulfillment automation`, or `awesome ecommerce skills`. Save the exact English queries. Search snippets and repository cards remain `candidate_screened`.

For one theme, compare two or three packages and record author/source, version, commit/tag, release, LICENSE, recent activity, issues/comments, PRs, discussions, security/advisories, credential/telemetry/executable risks, dependencies/cost, tests, T One overlap, and `platform + country/site + store_mode + ownership`. Sample one core workflow, one failure/boundary and three rules. Use only `keep_reuse / merge_into_existing / extract_rules_only / research_only / rejected_stale / rejected_license / rejected_unsafe`. Do not clone, install or execute during research. Unknown source/license, stale APIs, plaintext secrets, duplicate MCP/Skill/runtime, missing declared files, destructive tests or access-control evasion block reuse.

1. Read the authoritative memory and queue as read-only context, then this Skill, contract, evidence index, mother-fusion matrix, failure review, and last Shopee increment report.
2. Confirm the automation name is unique. Start with the existing-asset fusion ledger and package fingerprints, then pick one `repair_extend`, `merge_duplicate`, `remove_shell_candidate`, or `blocked_connector` delta; never create another Shopee expert/runtime/config surface.
3. Identify the real site/store execution identity and the available browser/software before choosing a lesson. A registry entry or tool name is not a connection.
4. Fingerprint known official URLs before rereading: canonical URL, title, publication/update time, ETag/Last-Modified where meaningful and content hash. Skip unchanged content and record only the cursor.
5. If an authorized Shopee environment exists, enter only that scoped environment and inspect menus, fields, status, native AI, help and developer/Ads entry points without a write. If no authorized store exists, use official public Seller/Developer/Ads/Help pages, an official demo, or a legal sandbox. 6. Classify each candidate as `candidate_screened`, `opened_not_reviewed`, `fully_reviewed`, or `blocked`. Actually open, click and scroll any reviewed software/page. Capture URL/product version, time, site, store mode, ownership, permission, clicked/scrolled functions, real inputs/outputs, console/page errors and the boundary reached. Screenshot or page presence alone is insufficient for a live fact.
7. Rotate sources: every round includes one first-party source plus one of community, allowed video/subtitles, or GitHub. A seller claim needs three independent sources and no official conflict before it may become a general hypothesis; a single claim stays a dated anecdote.
8. Prioritize the platform's own AI: entry, eligibility, accepted inputs, outputs, editing, submit/publish boundary, metrics and failure recovery. If access stops at login or eligibility, mark it `unknown` or `blocked_owner_input`.
9. Only after new external evidence exists, select the affected module and distill a rule. Seller experience is only an experiment hypothesis.
10. Capture canonical URL/content ID/title/author, publication/update and capture time, language, license/usage boundary, site, scope, validity, content hash and evidence grade. Assign one evidence level (`official_current`, `verified_software_observation`, `multi_source_practice`, `single_case`, `historical_trace`, or `unknown`) plus one knowledge status; do not collapse the two axes.
11. Deduplicate on `url + country_site + store_model + ownership + applies_to + content_hash`. If content is unchanged, update only the check cursor; do not duplicate or rewrite the rule. Keep superseded/expired evidence in a version chain.
12. Record conflicts and failed attempts. Weekly merge synonyms, detect conflicts and add counterexamples; monthly recheck stale rules, removed tools and evaluation coverage. Never promote research, a page, a button, a test, a draft, or an approval to a business outcome.
13. Preserve platform/category/tenant/task scope. Add a non-private_tenant anonymous case for every generic capability changed in the round; missing facts remain unknown.
14. Update only Shopee-owned Skill references, machine contract, tests, and increment report. Shared registry/core/queue/memory changes are recommendations only.
15. Add regression cases for new rules and failure modes; run the targeted unit tests and Skill validation.
16. Report in this fixed order: checked software/pages; duplicates skipped; new and superseded facts; distilled rules/evals; T One fusion improvements; tests and formal-entry validation; authorization blockers; next rotated source.

## Permanent source tracks

- Industry intelligence: site-specific policy, search/recommendation/Ads changes, developer APIs, payments/tax/compliance, logistics/warehouse/returns/settlement, official news/events and important service-provider changes. Record event time separately from publication and capture time; news stays time-sensitive.
- AI × ecommerce: official Shopee Listing/image/video/live/customer-service/Ads/analytics/compliance AI plus product understanding, creative, forecasting, inventory, CRM, fraud/compliance and ERP/workflow agents. Record provider, input/output, permissions, store isolation, site limits, price, data destination, human gate, errors, metrics and the distinction between announcement, beta, generally available, T One connected and live verified.
- Official open source: start from a first-party website/developer link, then index the organization and audit repository identity, README/docs, release/tag, LICENSE, issues/replies, discussions, PRs, security and recent commits. Deduplicate on `owner/repo + commit/tag`; never treat official-but-unrelated research as a Shopee connector.
- Social comments: treat the comment surface as an independent evidence source, not an optional footer check. It still cannot override current site-specific official evidence.

## Page and comment coverage

For every distilled source, record the visible table of contents/tabs/filters, author or official identity, publication/update time, version and site. Cover at least 90% of accessible content, scroll in segments to the footer, expand relevant “more,” FAQ, descriptions and transcripts, and follow at least one required second-level page. Infinite-scroll sources require at least three new loads and a recorded stop reason. Inspect first/next/latest list pages where present. For official technical documentation also inspect navigation, What's New/changelog, FAQ, limits, permissions, examples, errors/error codes and relevant SDK/official-GitHub links; a homepage or HTTP 200 is not mastery. Record covered sections, pagination and the exact unavailable region; never write “all read.” Stop after two link layers add no facts, the source becomes off-topic or duplicate, or login/CAPTCHA/MFA/paywall/platform limits appear.

For a video, social post or forum thread, inspect pinned/high-vote and latest views, author/official replies, nested replies, disputes and representative counterexamples; switch at least two comment sorts when supported. Record the number or range actually loaded, not a total-completion claim. Cluster anonymous themes for user questions, buyer intent, use cases, site/store mode, price objection, failures, returns, competitor comparison, tool needs and policy-change leads. Separate `official_reply`, `dated_operator_case`, `community_signal`, `conflicting_evidence`, sentiment/noise and suspected spam, affiliate, bot or synthetic repetition. Policy, fees, API and feature-change leads always return to current official evidence.

A video of 10 minutes or less qualifies only after at least 95% playback or at least 95% trusted platform-transcript coverage plus opening, core-operation, ending and available-comment checks. A long video requires complete trusted transcript/chapter coverage and verification of the opening, three core segments and ending; without a trusted transcript or chapters, play it completely. Record total duration, seconds played, transcript coverage, verified timestamps and comment count. A player at 0:00 or a cover/title/description-only view is `opened_not_reviewed`. A comment source qualifies only after at least 10 visible comment/reply items or proven review of every accessibly exposed item; fewer than 10 without proven completeness is `opened_not_reviewed` and cannot contribute a distilled cluster.

Deduplicate identical comment items across sorts before counting sources. Questions about money, sales, commission or conversion are demand signals only; creator replies without store-scoped metrics do not answer them. Use current official material for policy boundaries and authorized site/store reports for performance, while retaining `unknown` when either is absent.

When a community thread describes cross-shop listings or grouped product views, separate the observed buyer pain from the proposed mechanism. Recheck SSP/catalog linking, variation policy, Ads or AI claims independently; never infer shared authorization, review aggregation, shipping behavior or model use from repeated comments.

The owner authorizes the current logged Chrome session for read-only Shopee-professional learning when anonymous access is incomplete. Reuse its current cookies without copying them; never export tokens, read passwords, create an identity, change proxy/IP, open private messages or private groups, or like/follow/subscribe/save/comment/share/join/submit. Stop at login, CAPTCHA, MFA, phone, paywall or app authorization. Save only public URLs and anonymous theme summaries, never usernames, avatars, contacts or private content. Close only new unused tabs, not the owner's pre-existing pages.

No live publish, price, inventory, campaign, Ads, affiliate, shipment, refund, message, payment, settlement, authorization, MFA, bank, identity, or credential action is allowed in the training automation. If no new external page/software evidence exists, write a concise no-delta run record and do not manufacture or rewrite a lesson.

At least 70% of completed work in each run must directly serve one concrete Shopee site, store/program/fulfillment classification, listing/search/Ads/Affiliate/content/campaign/order/logistics/service/API capability, or its T One connector/evaluation. Tool or AI side tracks may consume at most 20%; a cross-platform reference requires an explicit migration hypothesis and may consume at most 10%. Mark off-topic material `irrelevant_skip`. Return all three shares, `scope_deviation_check`, `candidate_screened`, `fully_reviewed`, `opened_not_reviewed`, `blocked`, `irrelevant_skip`, `no_delta`, net facts, corrections, distilled assets and tests.
