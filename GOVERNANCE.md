# Governance

T One currently uses a maintainer-led model.

## Decisions

- Small implementation decisions are made through pull-request review.
- New public APIs, dependencies, write-capable connectors, security boundaries, and taxonomy changes require a design Discussion before implementation.
- Platform behavior claims should cite primary documentation and include the country/site and store mode.
- Security and privacy concerns override feature convenience.

## Maintainer responsibilities

- Keep the public/private boundary fail-closed.
- Review licensing and provenance of contributions.
- Preserve compatibility or publish a migration.
- Explain rejected changes in technical, respectful terms.
- Avoid promising platform support that has not been tested against a real authorized integration.

As the contributor base grows, governance can move to named module maintainers and a documented proposal process.
